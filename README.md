# Лілка · web IDE

Навчальне середовище для ігрової консолі [Лілка](https://lilka.dev) у браузері.

**Головна мета:** писати й запускати програми на Lua та mJS у браузері **точно
так само**, як вони працюють на залізі. Не «схоже», а піксель у піксель і кадр
у кадр.

Це не забаганка. Середовище призначене для навчання, і найдорожча помилка тут —
коли учень пише програму, вона працює у браузері, а на справжній Лілці
поводиться інакше. Тому весь код емулятора портований із прошивки рядок у
рядок, включно з особливостями, які виглядають як помилки.

Статичний сайт, без бекенду, розрахований на GitHub Pages.

---

## Швидкий старт

```bash
npm install
npm run dev        # http://localhost:5173 — відкривати в Chrome
```

Chrome обов'язковий: Lua виконується у Web Worker із `SharedArrayBuffer`, а це
вимагає заголовків COOP/COEP. Локально їх видає dev-сервер Vite, у продакшені —
`coi-serviceworker`. У Safari сторінка відкриється, але рантайм не запуститься.

Усі згенеровані файли вже в репозиторії — доганяти нічого не треба.

```bash
npm run check      # 76 автоматичних перевірок, усі мають бути зелені
npm run build      # tsc --noEmit + vite build -> dist/
```

Покриття Lua API: **80 зі 174 функцій**, з них у межах задуманого — 80 із 108
(74%). Різниця між 174 і 108 — апаратні простори імен, яких у браузері не буде
взагалі: `gpio`, `i2c`, `spi`, `pwm`, `wifi`, `mqtt`, `net`, `serial`, `ws2812`.

Перевірка «чи запуститься справжня програма» важливіша за відсоток. Гра
«Кубики» (близько 200 рядків: метатаблиці, три стани, звук, текст, геометрія)
проходить усі свої екрани від початку до виходу. Вона вбудована як приклад —
якщо колись перестане запускатися, це помилка емулятора, а не приклада.

Число оновлюється командою `npm run gen:coverage` — вона запускає справжній
рантайм, знімає перелік прив'язок і звіряє зі специфікацією, знятою з анотацій
прошивки.

## Архітектура

```
board.json ─┐
fonts/*.json├─> emulator ──> runtime ──> worker ─┐
fmath.ts ───┘   (малювання)  (Lua API)          │ SharedArrayBuffer
                                                 ▼
                                      головний потік ──> canvas
```

**Головна ідея розподілу:** темп задає **воркер**, а не головний потік. 30
кадрів на секунду з цілими 33 мс на кадр — рівно як `perfectDelta` у
`AbstractLuaRunnerApp::execute()`. Головний потік лише виводить те, що є, зі
своєю частотою. Дисплей на залізі теж оновлюється незалежно від того, як швидко
рахує програма, тож ця розв'язка не спрощення, а відтворення.

Кадрові буфери лежать у `SharedArrayBuffer`: воркер пише пікселі прямо в ту
пам'ять, яку головний потік виводить на екран. Копіювання між потоками немає.

Захист від `while true do end` — два незалежні шари: `debug.sethook` із
лічильником інструкцій (охайне завершення з номером рядка) і `worker.terminate()`
за відсутністю поступу понад 2 с (не залежить ні від чого всередині Lua).

## Правила, від яких залежить сенс проєкту

**1. Нічого про залізо не писати в коді руками.** Розміри екрана, піни, шрифти,
таблиці синусів, значення констант — усе генерується з коду прошивки скриптами
`gen-*`. Змінилася плата — змінився JSON, а не двадцять місць у коді.

**2. Особливості прошивки відтворювати, а не виправляти.** Якщо в первотворі є
помилка, емулятор мусить її повторити. Мета — збіг з реальним екраном, а не
«правильніше за прошивку». Кожна така особливість позначена коментарем і
закріплена тестом, щоб «виправлення» не проїхало непоміченим.

**3. Не використовувати Canvas 2D API для малювання.** `ctx.arc()`,
`ctx.lineTo()` згладжують краї й дають інші пікселі, ніж ST7789. Усе малюється
власними цілочисельними алгоритмами у `Uint16Array` формату RGB565.

**4. Кожна зміна має бути перевірена.** `npm run check` — 76 перевірок. Нова
функція без перевірки не вважається зробленою.

## Каталог особливостей заліза, відтворених навмисно

Це найцінніше знання проєкту. Кожен пункт знайдений читанням коду прошивки, і
кожен здатний зіпсувати урок, якщо його не відтворити.

**Екран 280×240, а не 240×280.** Панель справді 240×280, але `config.h` задає
`LILKA_DISPLAY_ROTATION 3`, а Arduino_GFX при повороті 1/3 міняє ширину з
висотою. Лілка — горизонтальна.

**Arduino_GFX робить кола не як Adafruit_GFX.** `drawCircle` викликає еліпсовий
хелпер, а не класичний midpoint. Наївний порт з Adafruit дав би інші пікселі.
Дуги (`draw_arc`/`fill_arc`) в Adafruit узагалі відсутні.

**`writeEllipseHelper` при `ry == 0` використовує `ry` там, де очікувався б
`rx`.** Схоже на помилку Arduino_GFX, але залізо поводиться саме так.

**Цілочисельне ділення відкидає дріб у бік нуля.** У `fillTriangle` і в
`Transform::transform` це `Math.trunc`, а не `Math.floor`. З `floor` заповнені
трикутники з від'ємним нахилом і обернені спрайти зсуваються на піксель.

**Обертання зображення без прозорого кольору дає БІЛІ кути.**
`drawImageTransformed` заповнює пікселі поза межами джерела значенням
`transparentColor`, а коли прозорого кольору немає, там лежить `-1`. У
`uint16_t` це `0xFFFF`.

**Тригонометрія — з таблиць прошивки, не з `Math.sin`.** `fmath.cpp` містить
`sin360[360]` зі значеннями на шість знаків після коми, оголошеними як `float`.
Відхилення від `Math.sin` до 5.3e-7 — дрібниця, доки не згадати про
`static_cast<int32_t>` після множення.

**`queueDraw()` міняє буфери місцями й нічого не очищає.** Програма щоразу
малює поверх кадру, який був **два** кадри тому. Скрипт без
`display.fill_screen` побачить не слід, а мерехтіння між двома старими кадрами.

**Текстовий стан належить канві, а канв дві.** Курсор, шрифт і колір у
Arduino_GFX — поля об'єкта канви. Отже `display.set_cursor`, викликаний один
раз, впливає лише на **один** із двох кадрів.

**`math` замінюється цілком, а не доповнюється.** `lualilka_math_register`
робить `luaL_newlib` і `lua_setglobal("math")`. На Лілці **немає** `math.huge`,
`math.fmod`, `math.tointeger`, `math.type`. Скрипт із ними працює у звичайній
Lua і падає на залізі.

**Ціле чи дробове видно в результаті.** Майже вся математика прошивки
віддається через `lua_pushnumber`, тобто завжди дробовим, і лише
`sign`/`floor`/`ceil`/`round` через `lua_pushinteger`. Тому `math.sin(0)`
друкується як `0.0`, а `math.floor(2.7)` як `2`. З тієї ж причини
`display.print` формує рядок у Lua через `tostring`, а не в JS.

**`math.random(a, b)` не включає верхню межу** — це семантика Arduino
`random()`, не Lua. **`math.round`** округлює половину від нуля (`roundf`), а
`Math.round` округлив би `-2.5` до `-2`. **`math.rotate`** рахує через таблиці
синусів прошивки і дробу не відкидає, на відміну від `Transform`.

**Послідовність запуску скрипта** з `luarunner.cpp`: очистити канву → виконати
тіло скрипта → `queueDraw` → **знову** очистити канву → `lilka.init` →
`queueDraw` → головний цикл. Два очищення не зайві: після обміну буферів друге
припадає вже на інший буфер.

**Шрифти — варіанти `t_cyrillic`**, і `glyph_cnt` у заголовку однобайтове: для
шрифту на 357 глифів там лежить 101.

**Розкладка кнопок праворуч:** C зверху, D ліворуч, A праворуч, B знизу.

**Простори імен — таблиці, а не userdata.** Об'єкти з боку JS приїжджають у Lua
проксі-об'єктами: індексування працює, але `type()` повертає `"userdata"`, а
`pairs` поводиться інакше. На залізі всі простори — звичайні таблиці, тож
преамбула перебирає їх у справжні таблиці.

**Глобальні таблиці `colors` і `notes`** реєструються прошивкою, але відсутні в
анотаціях LuaLS. Обидві відтворені; `notes` генерується з `enum Note` у
`buzzer.h`.

**Тривалість ноти:** `(60000 / tempo) / |size|` мілісекунд, і плюс половина,
якщо `size` від'ємний — це нота з крапкою. Частота 0 — пауза. `play_melody`
не блокує: у прошивці вона запускає окреме завдання.

## Що треба зробити

Порядок відображає залежності, а не важливість.

### 1. Більше справжніх програм

Найкорисніша перевірка — узяти написану для заліза програму й спробувати
запустити. Так знайшлися відсутній `buzzer`, відсутня таблиця `notes` і те, що
простори імен були userdata замість таблиць.

Кожна нова програма, яка запустилася, має ставати вбудованим прикладом у
`src/examples/`. Кожна, яка не запустилася, — назвати причину й закрити її.

### 2. Віртуальна файлова система

Розблоковує 6 заглушок і 12 нереалізованих функцій; покриття в межах задуманого
підніметься приблизно з 72% до 90%. Важливіше інше: майже кожна реальна
програма для Лілки вантажить спрайти з файлів, тож зараз такі програми не
запускаються взагалі.

- сховище: `IndexedDB` для файлів, `localStorage` для `state`
- дерево `/sd/...`, як на пристрої
- `resources.load_image` — **BMP**, і саме парсер прошивки визначає, які
  варіанти BMP працюють; треба звірити з `lilka::Resources::loadImage`
- `resources.read_file` / `write_file`, клас `File` (`exists`, `read`, `write`,
  `seek`, `size`), простір `sdcard`
- `state.save` / `clear` / `reset`
- в інтерфейсі: панель файлів із перетягуванням, щоб можна було кинути свій
  спрайт

### 3. Рантайм mJS

Друга мова, заявлена в меті.

`keira/lib/mJS/src/mjs.c` — це single-file амальгама, вже вендорена в keira.
Компілюється в WASM через `emcc` практично однією командою.

**Принципово не запускати код mJS у нативному движку браузера.** mJS — урізана
підмножина ES: браузер прийме код, який на залізі впаде. Для навчального
середовища це найгірший можливий різновид помилки.

Прив'язки мають бути ті самі, що для Lua. `src/runtime/bindings.ts` уже
відокремлений від мови, тож перевикористовується; різниця лише в шарі
маршалінгу значень і в преамбулі.

⚠️ mJS ліцензовано під **GPLv2 або комерційною** ліцензією Cesanta. Проєкт уже
позначений як `GPL-2.0-or-later` саме тому.

### 4. Нормальний редактор

Зараз це просте текстове поле. Потрібно:

- CodeMirror 6, підсвітка Lua та JS
- номери рядків і перехід до рядка з помилки (рантайм уже повідомляє
  `main.lua:3`, але клікнути нема куди)
- автодоповнення з `src/generated/lilka-api.json` — там уже є типи, параметри й
  українські описи всіх 174 функцій
- вкладки для кількох файлів, коли з'явиться файлова система

### 5. Blockly

Apache 2.0, з листопада 2025 під опікою Raspberry Pi Foundation. Штатно містить
генератори і Lua, і JavaScript — обидві цільові мови покриті з коробки.

Потрібні власні блоки для `display.*`, `controller.*`, `lilka.*` з двома
генераторами кожен. Визначення блоків варто генерувати з `lilka-api.json`, а не
писати руками, — інакше вони розійдуться з API при першій же зміні прошивки.

### 6. Web Serial — запуск на реальній Лілці

У keira вже є Live Lua над USB і REPL через serial, а в організації є
`lilka-dev/flasher` на Web Serial. Тобто кнопка «запустити на справжній Лілці» —
це перевикористання наявного коду, а не робота з нуля.

Chromium-only: у Firefox і Safari Web Serial немає.

### Дрібніше, але варте уваги

- **Мережа.** Офіційні приклади `lilka-dev/examples/tree/main/LUA` — це `http`,
  `httpserver`, `mqtt`, `socket`. Жоден зараз не запуститься. `http.execute`
  лягає на `fetch` (з обмеженням CORS), `mqtt` — на WebSocket, якщо брокер
  уміє; сирий TCP і сервер на пристрої в браузері неможливі принципово.
  Потрібні власні навчальні приклади — графічні, без мережі.
- **Віджети** `alertUI`, `keyboardUI`, `progressUI` і клас `File` — єдині
  прогалини в межах задуманого, окрім файлової системи.
- **Шеринг проєктів.** Бекенду немає, тож через хеш URL плюс імпорт/експорт
  файлів.
- **Інспектор пікселів.** `Screen.pixelAt()` уже написаний, інтерфейсу немає.

```bash
npm run check:runtime    # рантайм Lua
npm run gen:api          # перегенерувати lilka-api.json з keira
npm run gen:fonts        # перегенерувати шрифти (тягне ~40 МБ джерела, кешує)
npm run gen:fmath        # перегенерувати таблиці синусів
npm run gen:coverage     # звіт покриття API
npm run render:testcard  # PNG тест-карти; другий аргумент `images` — друга карта
```

Скрипти на `.mts` виконуються через `node --experimental-strip-types`, тож
потрібен **Node 22+**.

## Розгортання

`.github/workflows/deploy.yml` збирає й публікує на GitHub Pages. `VITE_BASE`
підставляється з назви репозиторію, тож сайт працює за адресою
`https://<owner>.github.io/<repo>/`. З власним доменом змінну можна не задавати.

`public/coi-serviceworker.js` мусить лишатися окремим файлом поза бандлом і
віддаватися з власного origin — інакше не буде `SharedArrayBuffer`, а без нього
не запуститься рантайм.
